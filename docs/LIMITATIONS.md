# Known limitations — 0.1

This is a working end-to-end development release (updated through 0.3), not completion of every item in the original product brief.

- Physical iPhone XS / iOS 18 performance, memory, battery behavior, camera capture, Safari installation and audio interruption recovery are unverified. The downloaded desktop WebKit test executable crashes at launch on this host. Chromium mobile emulation does not establish Safari compatibility.
- Real OMR evaluation currently uses one clean, original, four-bar grand-staff image. It is not a repertoire-wide accuracy benchmark. Recognition errors must be expected with photos, low contrast, skew, crowded systems, extra voices, handwritten notation, unusual clefs, tuplets, repeats and expressive markings. The engine is an upstream experimental port.
- The validation image's 19 sustained note events matched exactly, but its printed 96 BPM tempo was omitted. Missing numeric tempo explicitly defaults to 120 with a review warning. Set tempo after checking the original. Text-only tempo expressions are not interpreted.
- Repeat barlines, first/second endings, D.C., D.S., codas and segnos are displayed but not expanded for playback. Written measure order is used with a warning. Manual measure loops are implemented.
- Independent onset correction stays within the existing measure. Tied-note onset/duration edits need an external notation editor. Duration edits change subsequent XML cursor timing; check all voices after editing. Arbitrary notation insertion, deletion, enharmonic spelling and a complete notation engraving editor are not implemented.
- On-screen seeking supports the numbered measure strip and staff-position hit testing on the engraved score. The latter needs additional crowded/multisystem-score testing. The reconstructed score and originals are separate modes; the editor shows an original alongside its correction controls. Original-image note positions are not yet highlighted.
- Voice/staff IDs are preserved, but automatic right-/left-hand assignment is not asserted. Global instrument selection applies to pitched playback; MIDI track program identities are retained for export. True per-track sample-bank mixing and controller automation are not yet implemented.
- There are 128 selectable GM melodic sample banks. Piano is bundled, other banks need an initial GitHub download and MP3 decoding support. Only the active bank is decoded; piano plus the latest chosen bank are retained in persistent cache. GM percussion currently uses synthesized approximations rather than a full sampled drum kit. Sustain-pedal/controller, pitch-bend and channel automation from MIDI are not preserved.
- MIDI import builds explicitly timed MusicXML using independent voices. It is playable but may engrave awkwardly. Changing MIDI time signatures, tempo control text, multichannel details and performance-controller data need further work. Compressed `.mxl` and score-timewise XML are not supported; use uncompressed partwise MusicXML.
- Changing page part/staff counts use conservative page-specific tracks and sequential playback. Cross-page part identities are not inferred; this can create a large engraving for long documents. Completed XML checkpoints and rasterized import drafts are stored locally. PDF ranges and bounded previews are supported, while score-title OCR and automatic resume of unrendered PDF pages are not implemented.
- Image editing provides crop, rotation, deskew and contrast. Staff perspective is corrected by homr-rs; a four-corner whole-page perspective editor and full automatic global deskew are not provided. Browser EXIF/orientation behavior on the target iPhone still needs testing.
- PDF rasterization is sequential, but selected imported page images are retained as blobs until recognition/project storage. Extremely large PDFs can still exhaust browser memory. The recognition models themselves require about 158 MB of cached data plus significantly more runtime memory. No quantized replacement encoder or new training was introduced without an accuracy benchmark.
- The keyboard supports pointer multitouch, computer typing and permission-gated Web MIDI input, plus horizontal navigation with stepped zoom. Physical MIDI keyboards/audio interfaces have not been tested; output selection depends on browser permissions/API support. File-imported MIDI sustain/controller automation is distinct from the implemented live CC64 sustain handling. Native pinch zoom is not a dedicated keyboard gesture. OSMD cursor position is an approximate event-follow cursor and needs more complex-score validation. Acoustic output/display latency is not measured on a phone.
- English and Turkish cover navigation and core controls; technical help, status/error strings and some detailed editor text remain English.
- A self-hosted recognition HTTP service is not implemented. If a physical device proves unable to run the local models, the researched free fallback is homr CPU on the user's own computer, exporting MusicXML for local import. This does not conceal a cloud dependency.
- Offline storage is browser-managed and may be evicted. Back up projects outside Safari. WAV rendering has a bounded memory budget; long pieces should be exported as MIDI/MusicXML. No arbitrary score usage cap is imposed.
- GrandStaff training-data provenance and whether dataset licenses carry through to weights remain unresolved upstream. See THIRD_PARTY_NOTICES.md; the project does not assert complete legal clearance for all possible redistribution contexts.
